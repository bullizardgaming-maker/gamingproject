# Staging

A staging copy of the real stack: the API, Postgres, Redis and ClamAV on Render (`render.yaml`), and the web app on
Vercel pointed at it instead of the in-browser demo. It runs in **sandbox mode**: mock card checkout, mock KYC,
emails and SMS written to the log. Nothing on staging moves real money.

## 1. Domains

The refresh cookie is `SameSite=Strict`, so the web app and the API must share a registrable domain, for example:

| | Domain |
|---|---|
| Web (Vercel) | `staging.example.com` |
| API (Render) | `api-staging.example.com` |

With the default `*.vercel.app` and `*.onrender.com` hosts, sign-in works but the session is lost on every reload.
CORS allows exactly one web origin, so Vercel's per-branch preview URLs stay on demo data; only the staging domain talks
to the staging API.

## 2. API on Render

1. Render dashboard → **New → Blueprint** → this repository. Render reads `render.yaml` and creates the API service, the
   database, Redis and ClamAV.
2. Fill in the three values Render asks for:
   - `DATA_ENCRYPTION_KEYS`: `v1:` followed by 32 random bytes in base64. Generate with
     `echo "v1:$(openssl rand -base64 32)"`. Keep a copy: data encrypted with it can't be read without it.
   - `PUBLIC_WEB_URL`: `https://staging.example.com`
   - `PUBLIC_API_URL`: `https://api-staging.example.com`
3. `JWT_SECRET`, `FINGERPRINT_KEY` and `CRYPTO_INDEXER_SECRET` are generated by Render.
4. Add the custom domain `api-staging.example.com` to the API service.

Each deploy runs the migrations first (`preDeployCommand: node dist/migrate.js`); a failed migration stops the deploy
and the previous version keeps serving. The health check is `/readyz`, which fails only when the database is unreachable.

Sample data (optional): open the API service's **Shell** and run `node dist/seed.js`.

Background jobs run inside the API process (`RUN_WORKER_IN_PROCESS=true`) so that uploads stay on the one attached disk.
To run more than one instance, move uploads to S3 (`STORAGE_PROVIDER=s3`, `S3_BUCKET`) and add a worker service
running `node dist/worker.js`.

If uploads fail with `EACCES`, the disk is mounted root-owned while the image runs as `node`; switch uploads to S3 as
above rather than running the container as root.

## 3. Web on Vercel

In the Vercel project, add a **staging** environment (or use Preview scoped to a `staging` branch) with:

| Variable | Value |
|---|---|
| `VITE_DEMO` | `false` |
| `VITE_API_URL` | `https://api-staging.example.com` |

Assign `staging.example.com` to that environment. `VITE_API_URL` is added to the page's Content-Security-Policy at
build time, so redeploy after changing it.

## 4. Check it

- `https://api-staging.example.com/readyz` returns `"ok": true` with `"database": true` and `"pubsub": true`.
- Sign up on the staging site, reload: still signed in.
- Buy a listing: the mock checkout page opens and the order moves to paid.
- Upload a file in chat: ClamAV scans it (the first scan after a deploy waits for signatures to load).

## Moving to production

Staging leaves out what production needs: Stripe (`PAYMENT_PROVIDER=stripe` and its keys), Sumsub KYC, Postmark email,
Twilio SMS, S3 storage, the KMS escrow signer, a read replica and backups. `SANDBOX_MODE` must be off there. See
`docs/RUNBOOK.md`.
